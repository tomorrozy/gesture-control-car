# 一、刚体平面运动学基础

## 1.1 为什么差速底盘的运动学是线性的

差速底盘的运动可以拆成**两个独立运动的叠加**：

```
车身运动  =  整体平移（所有点速度相同）  +  绕中心自转（各点速度正比于到中心的距离）
```

这是刚体平面运动的**基本分解**，对任何刚体都成立。

关键在于：这两个运动的合成是**线性**的 —— 没有三角函数、没有乘积耦合。
所以：

```
轮速 = 平移贡献 + 旋转贡献        ← 可以直接相加
```

**这就是逆运动学能"叠加着推导"的数学依据**，也是为什么公式这么简单。

> [!note] 什么时候线性不再成立
> - 麦克纳姆轮 / 全向轮：轮速与车身速度是**矩阵关系**，仍然是线性的
> - 阿克曼转向（有舵机）：前轮转角与转弯半径是 `tan` 关系，**非线性**
> - 所以差速底盘是最容易分析的构型之一，这也是它适合入门的原因

## 1.2 符号约定（必须与代码一致）

| 符号 | 含义 | 单位 | 正方向 |
|---|---|---|---|
| `v` | 车身线速度 | m/s | 前进 |
| `ω` | 车身角速度 | rad/s | **逆时针（左转）** |
| `ω_L` / `ω_R` | 左/右**轮**角速度 | rad/s | 正 = 前进方向转 |
| `R` | 轮半径 | m | — |
| `L` | 轮距（两轮接地点中心距） | m | — |

> [!danger] ω 的正方向约定最容易出事
> 本工程约定 **ω > 0 = 左转（逆时针）**。
> 如果手带端和小车端约定相反，表现是**小车反向转**，
> 而且很难判断是"符号错"还是"接线错"。
> 代码里靠 `DMAP_ROLL_SIGN` 一个宏统一修正。

# 二、正运动学推导

## 2.1 轮子角速度 → 接地点线速度

**滚动无滑动**条件下，轮子转过的弧长等于它走过的距离：

```
走过的距离 = 轮子角速度 × 时间 × 半径
⇒ 线速度   = 轮子角速度 × 半径
```

```
v_L = ω_L · R
v_R = ω_R · R
```

## 2.2 平移分量

整体以 `v` 前进时，车身上**每一点**都有相同的速度 `v`。
特别地，左右轮接地点都有速度 `v`：

```
两者的平均 = (v + v) / 2 = v
```

## 2.3 旋转分量

绕中心以 `ω` 自转时，距中心 `d` 的点线速度为 `ω·d`。

左轮接地点在中心**左侧** `L/2` 处，逆时针自转时它向后运动：

```
旋转给左轮的速度 = −ω · (L/2)
旋转给右轮的速度 = +ω · (L/2)
```

## 2.4 叠加得到正运动学

```
v_L = v − (L/2)·ω
v_R = v + (L/2)·ω
```

反过来解出 `v` 和 `ω`：

```
① 两式相加：  v_L + v_R = 2v        ⇒  v = (v_L + v_R) / 2
② 两式相减：  v_R − v_L = L·ω       ⇒  ω = (v_R − v_L) / L
```

**这就是正运动学公式的完整推导。**

## 2.5 数值检验

| 工况 | v_L | v_R | 算出的 v | 算出的 ω |
|---|---|---|---|---|
| 直行 | 1 | 1 | 1 | 0 ✓ |
| 原地转 | −1 | 1 | 0 | 2/L ✓ |
| 前进+左转 | 1 | 2 | 1.5 | 1/L ✓ |

# 三、逆运动学（本工程使用）

把 2.4 节的式子解出 `v_L`、`v_R`：

```
v_L = v − (L/2)·ω
v_R = v + (L/2)·ω
```

再除以半径换成**轮子角速度**：

```
ω_L = (v − (L/2)·ω) / R
ω_R = (v + (L/2)·ω) / R
```

## 3.1 代码实现

```c
void Diff_BodyToWheel(float V, float Omega, float *WheelL, float *WheelR)
{
    float HalfTurn;
    HalfTurn = (WHEEL_TRACK_M * 0.5f) * Omega;      /* 旋转贡献，单位 m/s */
    *WheelL = (V - HalfTurn) / WHEEL_RADIUS_M;
    *WheelR = (V + HalfTurn) / WHEEL_RADIUS_M;
}
```

**只有 3 行** —— 因为推导已经把它化简到最简形式。

## 3.2 正逆互为逆运算（可自检的性质）

把逆解代回正解必须得到原值：

```
((v − h) + (v + h)) / 2 = v                    ✓
((v + h) − (v − h)) / L = 2h/L = (L·ω)/L = ω   ✓
```

> [!tip] 这是一个**可以自动验证**的性质
> `测试\测试差速数学.c` 的第 2 组测试就是干这个：
> 取 5 组随机 `(v, ω)`，正逆往返，误差必须 < 1e-4。
> 它等价于"公式推导正确"—— 不需要真机就能证明。

# 四、⭐ 电机能力包络（本阶段最核心的推导）

## 4.1 问题的发现过程

先看一个直觉上"应该没问题"的工况 —— 两个通道都取到映射上限：

```
v = 0.30 m/s,  ω = 2.00 rad/s
```

代入逆运动学（R = 0.0325, L = 0.2）：

```
ω_L = (0.30 − 0.1 × 2.00) / 0.0325 =  3.08 rad/s
ω_R = (0.30 + 0.1 × 2.00) / 0.0325 = 15.38 rad/s
```

电机满 PWM 只有 **11.0 rad/s**。**右轮需求超了 40%。**

这个问题的隐蔽性在于：
- 单独用 v（直行）没问题
- 单独用 ω（原地转）也没问题 —— 原地转两轮只要 ±6.15
- **只有"大 v + 大 ω"同时出现才爆发**

## 4.2 后果量化

右轮不可能超过 11.0，所以实际给到 11.0。用正运动学反算**实际**运动：

```
实际 ω_L = 3.08      （未饱和，正常）
实际 ω_R = 11.00     （被削掉了 4.38）

实际 ω = (ω_R − ω_L)·R / L
       = (11.00 − 3.08) × 0.0325 / 0.2
       = 1.29 rad/s
```

| 项 | 指令 | 实际 | 误差 |
|---|---|---|---|
| v | 0.30 m/s | (3.08+11.00)×0.0325/2 = 0.229 m/s | −23.7% |
| **ω** | **2.00 rad/s** | **1.29 rad/s** | **−35.6%** |

**表现**：转弯半径从 `v/ω = 0.15 m` 变成 `0.229/1.29 = 0.178 m`。
用户想急转，实际车画出更大的弧 —— 这就是"**车往外甩**"。

> [!warning] 为什么这个 bug 特别难查
> 因为 PID 参数、编码器方向、接线**全都是对的**。
> 波形上看，两个 PID 都在正常工作（一个跟得上、一个撞上限）。
> 只有把"指令 ω"和"实际 ω"放在一起对比才会发现差异。

## 4.3 约束的数学形式

要求两轮都不超上限 `Ωmax`：

```
|ω_L| ≤ Ωmax    且    |ω_R| ≤ Ωmax
```

代入：

```
|v − (L/2)ω| / R ≤ Ωmax
|v + (L/2)ω| / R ≤ Ωmax
```

令 `A = Ωmax · R`（电机能给的最大**轮子线速度**），整理：

```
|v − (L/2)ω| ≤ A        … ①
|v + (L/2)ω| ≤ A        … ②
```

## 4.4 解出 v 的上限

设 `h = (L/2)|ω| ≥ 0`。分两种情况：

**情况 A：v 与 ω 同号**（左前弧线、右后弧线，最紧的情况）

```
① ⇒ −A ≤ v − h ⇒ v ≤ A + h
     且 v − h ≤ A ⇒ v ≤ A + h        （v ≤ A+h 更松）
② ⇒ −A ≤ v + h ⇒ v ≥ −A − h
     且 v + h ≤ A ⇒ v ≤ A − h        （更紧！）
```

所以 `v ≤ A − h`。

**情况 B：v 与 ω 异号**

同理可推出 `|v| ≤ A − h`。

两种情况合并：

```
┌──────────────────────────────┐
│   |v| ≤ A − (L/2)|ω|         │   ← 包络约束
└──────────────────────────────┘
```

**若右边 ≤ 0**，说明"光转就已经把电机用满了"，此时 `v` 只能取 0。

## 4.5 数值表（A = 11.0 × 0.0325 = 0.3575 m/s）

| ω (rad/s) | (L/2)·ω | v 上限 (m/s) | 说明 |
|---:|---:|---:|---|
| 0 | 0 | **0.3575** | 全速直行 |
| 0.5 | 0.05 | 0.3075 | 轻微转向，几乎不损失速度 |
| 1.0 | 0.10 | 0.2575 | |
| 2.0 | 0.20 | **0.1575** | 最大的映射角速度，速度余量被压掉一半以上 |
| 3.0 | 0.30 | 0.0575 | 快到极限了 |
| 3.575 | 0.3575 | **0** | 只剩原地转 |

## 4.7 ⚠️ 只限 v 是不够的（穷举自检抓出来的缺口）

很多人（包括本文档的第一版）会以为 4.4 节的式子已经完备了。**并不。**

问题在于：当 `|ω| > A/(L/2)` 时，`A − (L/2)|ω|` 变成负数，
代码里把它钳到 0，于是 `v` 被限制成 0。看起来很安全。

**但 v = 0 并不等于安全**。原地转时两轮转速是：

```
|ω_L| = |ω_R| = (L/2)|ω| / R
```

要让它们不超 `Ωmax`：

```
(L/2)|ω| / R ≤ Ωmax
⇒ |ω| ≤ Ωmax·R / (L/2) = A / (L/2)
```

代入本工程参数：

```
ω 上限 = 0.3575 / 0.1 = 3.575 rad/s  （约 205°/s）
```

**验证**：若 `ω = 4.0`，即使 `v = 0`：
两轮需求 = `0.1 × 4.0 / 0.0325 = 12.31 rad/s` → **双双超过 11.0**。

### 穷举验证结果

`测试\测试差速数学.c` 的第 10 组做了穷举：

| 钳位策略 | 扫描组数 | 反例数 |
|---|---:|---:|
| 只限 v | 1,442,401 | **86** |
| **先限 ω、再限 v** | 1,442,401 | **0** |

且第二种策略**不误伤**本来就合法的指令。

### 完整的两段钳位

```
① ω ← clamp(ω, ±Diff_MaxOmega())          Diff_MaxOmega() = A/(L/2)
② v ← clamp(v, ±Diff_MaxVForOmega(ω))     Diff_MaxVForOmega(ω) = A − (L/2)|ω|
```

> [!note] 本工程实际不会触发第 ① 步
> 手带端的 ω 映射上限是 2.00 rad/s，远小于 3.575。
> 但小车端作为"最后的栅栏"必须做全 ——
> 否则一旦收到错帧或噪声，这个缺口就会暴露。
>
> **"当前参数下不会发生"不是"不需要写"的理由。**

# 五、为什么选择「保住 ω、让掉 v」

包络生效时会**同时削减 v 和 ω 中的一个**（不能两个都保）。选择依据：

| 让掉谁 | 物理后果 | 用户感知 | 评价 |
|---|---|---|---|
| 让掉 **v** | 走得慢一点，转弯半径不变 | "怎么变慢了" | ✓ 可接受 |
| 让掉 **ω** | 转弯半径变大，**走错路线** | "怎么转不过去" | ✗ 安全问题 |

**判断原则**：

> 转弯是**有意图**的操作（用户明确打了方向，有目的地）；
> 速度只是**快慢**（程度问题，没有目的性）。
> 两个都做不到时，优先满足有意图的那个。

## 5.1 这不只是"取舍"，也是真实物理

需要强调：**「全速前进 + 急转」在差速底盘上物理不可能**。
这不是代码为了省事做的妥协，而是：

```
两个轮子的量程只有 2 个自由度
而 v 和 ω 需要 2 个自由度
→ 当 (v, ω) 同时取大，需求超出量程
```

任何差速机器人都面临这个约束（扫地机器人、AGV、坦克都一样）。
工程上的标准做法就是"降速保转向"。

# 六、硬件原理

## 6.1 TB6612 驱动芯片

### 6.1.1 为什么需要驱动芯片

STM32 的 GPIO 输出能力是 **3.3V / 约 20mA**，而电机需要 **12V / 数百 mA 到数 A**。
驱动芯片的作用是"**用小信号控制大电流**"。

```
STM32 GPIO (3.3V, mA 级)  →  TB6612  →  电机 (12V, A 级)
                               ↑
                        外部 12V 电源（VM）
```

### 6.1.2 TB6612 内部结构

单个 TB6612 有**两路** H 桥（A、B），正好驱动左右两个电机：

```
        ┌──────────── TB6612 ────────────┐
 PWMA ─►│ ── H桥A ── AOUT1 ─────────────►│── 左电机
 AIN1 ─►│           AOUT2 ─────────────►│
 AIN2 ─►│                                │
        │                                │
 PWMB ─►│ ── H桥B ── BOUT1 ─────────────►│── 右电机
 BIN1 ─►│           BOUT2 ─────────────►│
 BIN2 ─►│                                │
 3.3V ─►│ STBY（整芯片使能，高有效）     │
        └────────────────────────────────┘
```

**H 桥**：4 个 MOSFET 排成"H"形，电机在中间横杠上。
通过导通不同的对角组合，可以改变电流方向 → 电机正反转。

### 6.1.3 真值表

| AIN1 | AIN2 | PWM | 状态 |
|:--:|:--:|:--:|---|
| 0 | 0 | X | **自由停止**（滑行，不发力） |
| 0 | 1 | 有效 | 正转 |
| 1 | 0 | 有效 | 反转 |
| 1 | 1 | X | **刹车**（绕组短路制动） |

> [!important] 「自由停止」和「刹车」的区别（题目要求"不发力"）
> | | 自由停止 (00) | 刹车 (11) |
> |---|---|---|
> | 电机两端 | 悬空 | 短路 |
> | 反电动势 | 无回路，不产生电流 | 形成制动电流 |
> | 效果 | 靠惯性滑行慢慢停 | 快速制动 |
> | 是否"发力" | **否** | 有制动力 |
>
> 题目要求的"不发力"= **自由停止**，所以 `Motor_Stop()` 用 `AIN1=AIN2=0`。

### 6.1.4 STBY 接 3.3V 的理由

| 方案 | 优点 | 缺点 |
|---|---|---|
| 软件控 GPIO | 可以进入待机省电 | 占 1 个 GPIO；复位瞬间状态不确定 |
| **接 3.3V（本工程）** | 省 GPIO；使能状态由硬件保证 | 无法软件待机 |

本项目不需要待机，而 GPIO 比"待机省电"珍贵得多。

> [!danger] 改线的坑
> PA3 在七阶段是 STBY，八阶段变成**右电机 PWM**。
> 若线没拔掉，PWM 波形会不停开关整芯片使能
> → 电机**抽搐、时转时停**。

## 6.2 PWM 频率的选择

```
72 MHz / (PSC+1=36) = 2 MHz          计数时钟
2 MHz / (ARR+1=100) = 20 kHz         PWM 频率
占空比 = CCR / 100                    ⇒ CCR 直接是百分数
```

**为什么选 20 kHz**：

| 频率 | 问题 |
|---:|---|
| 1 kHz 以下 | **落在人耳听觉范围内**，电机发出刺耳啸叫 |
| 1 ~ 8 kHz | 仍然听得到 |
| **20 kHz** | 高于听觉上限（约 20kHz），**不啸叫** |
| 远高于 20 kHz | 开关损耗增加，H 桥可能来不及响应 |

20 kHz 同时远快于电机的**机械时间常数**（毫秒级），
所以占空比能平滑地表示平均电压（≈ 平均转矩），不会造成转速抖动。

## 6.3 双路 PWM 共用一个定时器的代价与收益

| | 收益 | 代价 |
|---|---|---|
| 同一 TIM2 的 CH3 + CH4 | 两路**频率天然完全同步**，无拍频 | 两路只能同频，不能独立改 |

如果两路用不同定时器，频率会有微小差异（比如 20.000 kHz 和 19.998 kHz），
合成转矩会出现**差频拍振**（几十 Hz 的周期性抖动），
表现为小车低速爬行时有规律的顿挫。

> [!warning] 初始化顺序的坑
> `TIM_TimeBaseInit()` 会覆盖时基寄存器，但**不会动 CCMR**（通道配置）。
> 正确顺序：**先配时基一次，再配两个通道**。
> 反过来的话，先配好的通道会被后来的操作影响。

# 七、编码器接口原理

## 7.1 为什么编码器接口要独占一个定时器

AB 相编码器输出两个方波，相位差 90°。**转向信息藏在相位关系里**：

```
正转：A 相上升沿时 B 相为低
反转：A 相上升沿时 B 相为高
```

STM32 的**编码器接口模式**用硬件实现这个判断：

```
TIMx_CH1 ← A 相
TIMx_CH2 ← B 相
```

硬件自动根据两相的边沿把计数器 `+1` 或 `−1`。
**CPU 完全零负担** —— 不需要任何中断。

> [!important] 这就是为什么"必须独占" 
> 编码器接口需要 **CH1 和 CH2 两个通道**（要同时看 A、B 两相）。
> 这不是软件限制，是硬件电路决定的：
> 计数器必须有"两个输入"才能判断方向。
>
> STM32F103C8T6 只有 TIM2/3/4 三个通用定时器，所以：
> ```
> TIM2 → 双路 PWM
> TIM3 → 左编码器
> TIM4 → 右编码器  ← 全部用满，没有余量
> ```

## 7.2 四倍频

一个完整的 AB 相脉冲周期内，**有 4 个边沿**：
A 上升、B 上升、A 下降、B 下降。
硬件在每个边沿都计数 → 分辨率提高 4 倍。

```
每转计数 = 线数 × 减速比 × 4
         = 13 × 30 × 4 = 1560
```

> [!tip] 校验方法
> 用手把输出轴**正好转一圈**，累计计数应等于 1560。
> 对不上说明 `ENCODER_PPR` 或 `ENCODER_GEAR_RATIO` 填错了。

## 7.3 转速计算

计数器给的是**累计脉冲**，要变速度必须除以时间：

```
转速(rad/s) = (Δ计数 / 每转计数) × 2π / 采样周期(秒)
```

**所以 `Encoder_Update()` 必须由固定周期调用**，否则算出的速度不准。
本工程由 SysTick 每 10ms 调用一次。

## 7.4 ⚠️ 左右轮符号一致性（正反馈陷阱）

底盘两侧电机**镜像安装**，常导致右轮的 A/B 相接反。
表现是：

```
给正 PWM → 左轮读数为正，右轮读数为负
```

**后果**：右轮的速度环变成**正反馈**：

```
目标 +8，实际 −1  →  误差 9  →  输出更大  →  实际更负  →  误差更大  →  飞车
```

### 验证方法（上电必做）

1. 架起小车（电机悬空）
2. 给一个固定的小正 PWM（开环，PID 不参与）
3. 看 OLED 上两轮的**实际转速**是否都为正
4. 某一路为负 → 把对应的宏改成 −1：

```c
#define ENCODER_DIR_L    (+1.0f)     /* 左轮反了改成 -1 */
#define ENCODER_DIR_R    (+1.0f)     /* 右轮反了改成 -1 */
```

> [!danger] 这一步不做就开 PID，一上电小车就飞出去
> 七阶段的 README 就专门警告过这一点（那时只有一个电机），
> 八阶段有**两路**，出问题的概率翻倍。

# 八、JTAG 与 PB3/PB4

## 8.1 引脚默认归属

STM32F103 复位后，5 个引脚被 JTAG 占用：

| 引脚 | JTAG 功能 | 我们是否需要 |
|---|---|---|
| PA13 | JTMS / **SWDIO** | **需要**（SWD 下载） |
| PA14 | JTCK / **SWCLK** | **需要**（SWD 下载） |
| PA15 | JTDI | 不需要 |
| **PB3** | **JTDO** | 不需要，但**我们要用作 GPIO** |
| **PB4** | **NJTRST** | 不需要，但**我们要用作 GPIO** |

STM32 支持"只保留 SWD、关掉 JTAG"：**2 根线就能下载调试**，
另外 3 根线（PA15/PB3/PB4）被释放成普通 GPIO。

## 8.2 配置代码

```c
RCC_APB2PeriphClockCmd(RCC_APB2Periph_AFIO, ENABLE);
GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE);
```

> [!danger] 两个宏的区别（用错会锁死调试口）
> | 宏 | JTAG | SWD | 后果 |
> |---|:--:|:--:|---|
> | `GPIO_Remap_SWJ_JTAGDisable` | 关 | **留** | ✓ 正确 |
> | `GPIO_Remap_SWJ_Disable` | 关 | **关** | ✗ **再也下载不进程序** |
>
> **用错第二个宏怎么救**：
> 把 BOOT0 拉高 → 复位 → 芯片从系统存储器（Bootloader）启动，
> 此时外设还没被初始化，可以用串口 ISP 重新烧写。
> 或者用 ST-Link 的 "Connect under Reset" 模式。
>
> 这是个很痛的教训，所以在代码里写成了 `Board.c` 独立模块 + 显眼注释。

## 8.3 现象识别表

| 现象 | 可能原因 |
|---|---|
| 左轮正常、**右轮完全不动** | **PB3/PB4 忘禁 JTAG**（首要怀疑） |
| 两轮都不动、OLED 正常 | TB6612 的 VM 没接 12V 或 STBY 没拉高 |
| 右轮时转时停、抽搐 | PA3 还接在 STBY 上（应改接 3.3V） |
| 编译报 `Board_Init` 未定义 | 没把 `Board.c` 加进 Keil 工程 |

# 九、定时器资源分配与 SysTick

## 9.1 资源总账

STM32F103C8T6 的定时器资源：

| 定时器 | 类型 | 位宽 | 第八阶段用途 |
|---|---|---|---|
| TIM1 | 高级 | 16 位 | 空闲（预留给进阶拓展） |
| TIM2 | 通用 | 16 位 | **双路 PWM**（CH3 PA2 / CH4 PA3） |
| TIM3 | 通用 | 16 位 | **左编码器**（PA6/PA7） |
| TIM4 | 通用 | 16 位 | **右编码器**（PB6/PB7） |
| SysTick | 内核 | 24 位 | **10ms 控制周期** |

## 9.2 SysTick 是什么

**它不是 STM32 的外设，是 ARM Cortex-M 内核自带的** 24 位递减计数器。
ARM 设计它本来是给 RTOS 做系统节拍（FreeRTOS 的 `vTaskDelay` 就靠它）。

寄存器只有 4 个：

| 寄存器 | 作用 |
|---|---|
| `CTRL` | 使能、时钟源、中断使能 |
| `LOAD` | 重装载值（24 位，最大 0xFFFFFF） |
| `VAL` | 当前计数值（写它可清零） |
| `CALIB` | 校准值（本项目不用） |

## 9.3 周期计算

```
SysTick 时钟源 = 内核时钟 = 72 MHz
要 10 ms  →  需要数 72 MHz × 0.01 s = 720000 个周期
```

```c
SysTick_Config(720000);      /* CMSIS 标准函数 */
```

`SysTick_Config()` 内部会：
- 把 `重装载值 − 1` 写进 `LOAD`（硬件从 LOAD 递减到 0，共 LOAD+1 个周期）
- 清零 `VAL`
- 选内核时钟源、开中断、开计数器

返回 0 表示成功，唯一失败情况是参数超过 24 位上限。
校验：`720000 < 16777215` ✓

## 9.4 为什么 SysTick 在第八阶段特别合适

| 对比项 | TIM4（七阶段） | **SysTick（八阶段）** |
|---|---|---|
| 占用外设 | 通用定时器 | **内核，不占外设** |
| 中断优先级 | 可配 0~15 | **内核级，高于所有外设中断** |
| 移植性 | 换芯片要改 | Cortex-M 全系通用 |
| 代码量 | 配时基/中断/清标志 | 一个 `SysTick_Config()` |

**"内核级优先级"这一点在第八阶段很关键**：
PID 必须在**严格固定**的 10ms 里跑完（离散 PID 的参数隐含了采样周期）。
SysTick 优先级高于串口、编码器读取等外设中断，保证控制周期不被顶掉。

## 9.5 与 TIMx 中断的两个差异（容易踩）

| 项 | TIMx_IRQHandler | SysTick_Handler |
|---|---|---|
| 函数名 | 可自己选（但要和启动文件一致） | **固定为 `SysTick_Handler`** |
| 清中断标志 | 必须手动 `TIM_ClearITPendingBit()` | **读 CTRL 时硬件自动清** |

**对外接口完全不变**：`Timer_Init()` / `Timer_GetMs()` / `Timer_TickHook()`
—— 所以两端 `main.c` 的结构一行都不用改，只是链接进来的
`Timer.c` 换了实现。

# 十、协议扩展的一般方法

## 10.1 判断"要不要改协议"的准则

```
新需求的信息，能不能用已有字段表达？
    能   → 不要改协议（改协议要两端同步，成本高）
    不能 → 必须改，且两端一起改
```

## 10.2 三种"看起来能省"的投机方案，为什么都不行

| 方案 | 致命缺陷 |
|---|---|
| 用 int16 的高几位表示转向 | 分辨率的**自由度互相挤占**：v 和 ω 都要精度，不能共用位 |
| 每帧交替发 v 和 ω | **时间不同步**：转弯时小车拿到的是"上一拍的 v + 这一拍的 ω"，画折线 |
| 发左轮速度 + 右轮速度 | 信息等价、**其实可行**，但① 小车端无法显示"车身 v/ω"；② 换成麦克纳姆轮时两端都要改 |

> [!tip] 第三种方案值得多说一句
> 它不是"错"，而是**抽象层次选低了**。
> 发 `(v, ω)` 是"与底盘无关的运动意图"，换轮径、换底盘、换构型，
> 手带端都不用改；发轮速则把底盘几何**泄漏**到了协议里。

## 10.3 带宽核算（每改一次协议都要重算）

9600 波特率、8N1 格式（**每字节实际传 10 位**：1 起始 + 8 数据 + 1 停止）：

| 阶段 | 整帧长度 | 单帧耗时 | 心跳 20ms 时的占用 |
|---|---:|---:|---:|
| 七阶段 | 8 字节 | 8.33 ms | 41.7% |
| **八阶段** | **10 字节** | **10.42 ms** | **52.1%** |

**结论**：9600 下 50Hz 勉强可用，但已经过半，没有余量了。
若要提到 100Hz（10ms 心跳），必须改用 115200：

| 波特率 | 10 字节耗时 | 20ms 心跳占用 | 10ms 心跳占用 |
|---:|---:|---:|---:|
| 9600 | 10.42 ms | 52.1% | 104% ✗ **不可能** |
| 115200 | 0.87 ms | 4.3% | 8.7% ✓ |

> [!note] 协议设计的一个通用教训
> 「长度驱动 + 通用帧」的设计（一阶段定的）在这里体现出价值：
> 数据区从 3 字节扩到 5 字节，**帧格式、校验规则、解析状态机全都不用改**，
> 只需要两端把数据区的内容重新解释一遍。

# 十一、引脚规划的系统方法

## 11.1 为什么第八阶段必须重排引脚

第八阶段相比七阶段，硬件上多了**一整套**执行/反馈链路：

| 资源 | 七阶段 | 八阶段 | 增量 |
|---|:--:|:--:|:--:|
| PWM 通道 | 1 | 2 | +1 |
| 方向控制脚 | 2 | 4 | +2 |
| 编码器接口 | 1 | 2 | **+1 个整个定时器** |

**关键约束**：编码器接口必须独占定时器的 CH1+CH2，
而 C8T6 只有 3 个通用定时器 → **双 PWM 用掉 1 个，双编码器用掉 2 个，一个不剩。**

## 11.2 规划步骤（可复用的方法）

```
① 先数"必须独占整个外设"的资源（编码器接口、PWM 定时器）
   → 这类资源最稀缺，优先分配
② 再分配有"默认引脚"的外设（USART、I2C、SPI）
   → 它们的引脚由硬件固定，能动的是"选哪个外设"
③ 最后分配纯 GPIO（方向脚、按键、LED）
   → 这些可以随便挪，弹性最大
④ 检查三个"隐藏冲突"：
   · JTAG 占用的 5 个引脚（PA13/14/15、PB3/4）
   · 晶振引脚（PD0/PD1，本工程用内部晶振所以空闲）
   · BOOT0/BOOT1、NRST 等专用引脚
⑤ 把结论写成一张表，代码里的宏与表一一对应
```

## 11.3 本工程的分配结果与理由

| 功能 | 引脚 | 为什么是它 |
|---|---|---|
| 左 PWM | PA2 (TIM2_CH3) | 沿用七阶段，不动 |
| 右 PWM | PA3 (TIM2_CH4) | **与左 PWM 同一定时器** → 频率天然同步；且 PA3 原为 STBY，腾出来正好 |
| 左编码器 | PA6/PA7 (TIM3) | 沿用七阶段 |
| 右编码器 | PB6/PB7 (TIM4) | TIM4 的**默认** CH1/CH2，不用重映射 |
| 右方向 | PB3/PB4 | 空闲（禁 JTAG 后可用），且离其他功能远 |
| MPU6050 | PB8/PB9 | **与 OLED 共用软件 I2C 总线**（地址不同即可共存） |
| OLED | PB8/PB9 | 沿用七阶段，且江科大 `OLED.c` 写死 PB8/PB9，不动它 |
| 蓝牙 | PA9/PA10 | USART1 固定引脚 |
| 按键 | PB1 | 沿用 |

## 11.4 一个"少占两个引脚"的技巧：I2C 共总线

MPU6050 原本（五~七阶段）在 PB6/PB7，第八阶段被右编码器抢走。
备选是把 MPU6050 挪到 PB10/PB11 —— 但 **PB11 是按键 K2**，得取消按键。

**更好的方案**：把 MPU6050 也挂到 OLED 那条总线（PB8/PB9）。

| 设备 | 7 位地址 | 8 位地址 |
|---|---|---|
| OLED (SSD1306) | 0x3C | 0x78 |
| MPU6050 (AD0 接 GND) | 0x68 | 0xD0 |

地址不冲突；I2C 是"开漏 + 上拉"总线，**天生支持多设备共线**；
上拉电阻由 OLED 模块板载的 4.7kΩ 提供。

**收益**：省下 PB10/PB11，**按键 K2 得以保留**，且接线更少。

> [!tip] 这是五阶段"选软件 I2C"的远见回报
> 硬件 I2C1 固定在 PB6/PB7 上 —— **根本挪不动**，也没有"共总线"的自由度。
> 而软件 I2C 完全由引脚宏参数化，换引脚只改两行宏，驱动代码零改动。
>
> **选技术方案时，"将来能不能改"往往比"现在快不快"更重要。**

# 十二、单位与量纲（最容易写混的地方）

## 12.1 三套"速度"的区别

| 量 | 符号 | 单位 | 在本工程里的位置 |
|---|---|---|---|
| **轮子角速度** | ω_L, ω_R | rad/s | 编码器读数、PID 的目标与反馈 |
| **轮子接地点线速度** | v_L, v_R | m/s | 中间量（= ω × R） |
| **车身线速度** | v | m/s | 手带端映射输出、协议传输 |
| **车身角速度** | ω | rad/s | 手带端映射输出、协议传输 |

> [!danger] 坑：`ω` 这个符号被用了两次
> - `ω_L` / `ω_R` 是**轮子**角速度（轮子自己转多快）
> - `ω` 是**车身**角速度（车整体转多快）
>
> 两者量纲相同（rad/s），**非常容易混**。
> 代码里刻意用不同命名区分：轮子一律带 `Wheel` 前缀或 `_L/_R` 后缀。
>
> **量纲检查法**：写公式时把单位代进去算一遍。
> 比如 `HalfTurn = (L/2)·ω`：`m × rad/s`，而 rad 是无量纲的 → 结果单位是 `m/s` ✓
> 所以 `HalfTurn` 是**线速度**，与 `v` 可以直接相加减。这一步检查能挡掉大量错误。

## 12.2 角度与弧度

| 项 | 换算 |
|---|---|
| 1 rad | ≈ 57.29578° |
| 1° | ≈ 0.017453 rad |
| 2.00 rad/s | = 114.6 °/s，原地转一圈需 3.14 s |

**本工程约定**：
- **姿态角**（Pitch/Roll）用**度**（因为映射阈值写成 4°、45° 更直观）
- **角速度**（ω）用 **rad/s**（因为要和轮速 rad/s 直接做运动学运算）

> [!warning] 混用会导致 57 倍的错误
> 如果误把 `2.0 rad/s` 当成 `2.0 °/s`，小车几乎不转；
> 反过来把 `45°` 当成 `45 rad`，就是转了 7 圈多。
> 代码里所有角度相关变量都在注释里标了单位。

## 12.3 前缀与缩放

协议里 `v` 和 `ω` 都 **×100** 传输（`DMAP_SCALE = 100.0f`）：

| 物理值 | 传输值 |
|---|---|
| v = 0.30 m/s | 30 |
| ω = 2.00 rad/s | 200 |
| 分辨率 | 0.01（m/s 或 rad/s） |

int16 范围 ±32767 → 可表示 ±327.67，**超出物理可能范围两个数量级**，不会撞顶。

**为什么必须缩放**：直接取整的分辨率是 1 m/s，PID 完全没法用。
