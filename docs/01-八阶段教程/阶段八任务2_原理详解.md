# 阶段八 任务2 原理详解

> [!info] 这篇文档解决什么问题
> 题目说「**运动平稳，响应及时**」。这八个字里其实藏着三组技术问题：
> ① 前馈为什么能让 PID 既快又稳（含数值对比）
> ② 为什么必须两个独立的闭环
> ③ 中断里能做什么、不能做什么（本阶段踩过两个真实的坑）

# 一、「响应」与「平稳」为什么天生冲突

## 1.1 冲突的数学根源

对一个速度环，误差的动态方程可以近似写成：

```
de/dt = -Kp·K·e - Ki·K·∫e dt
        └────┬────┘  └────┬────┘
         比例项作用      积分项作用
```

（`K` 是被控对象的稳态增益：`轮速 = K × PWM`）

| 想达到 | 参数怎么调 | 副作用 |
|---|---|---|
| **响应快**（误差快速变小） | 加大 `Kp`，加大 `Ki` | 误差过零后来不及刹车 → **超调、振荡** |
| **平稳**（不振荡） | 减小 `Kp`，减小 `Ki` | 误差衰减慢 → **响应肉、有静差** |

**这是一个单自由度的妥协**：只有一个"增益"可调，快和稳只能二选一。

## 1.2 数值验证（可复核）

`测试\分析前馈对比.py` 用明确写出参数的一阶模型做仿真：

```
稳态轮速 = 0.110 × PWM  →  PWM 100 时 11.0 rad/s
机械时间常数 τ = 60 ms
等效摩擦死区 = 0.35 rad/s
控制周期 = 10 ms（含积分限幅 + 条件积分抗饱和）
目标 = 6.00 rad/s
```

| 方案 | 进入 ±5% 用时 | 超调 | 稳态误差 |
|---|---|---|---|
| 纯反馈 Kp=8.0 Ki=1.2 | **> 2000 ms** | 0% | **−49.7%** |
| 纯反馈 Kp=8.0 Ki=10.0 | **> 2000 ms** | 0% | **−19.9%** |
| **前馈+反馈 Kp=5.0 Ki=0.5** | **140 ms** | 0% | −3.4% |
| **前馈+反馈 Kp=8.0 Ki=1.2** | **100 ms** | 0% | −2.6% |

> [!warning] 这是仿真值，不是实测值
> 真机的摩擦/负载特性远比一阶模型复杂，**具体数字一定会变**。
> 表格的价值在于展示**趋势和量级**，不要当成实测结论。
> 参数全部写在脚本里，任何人都能复核或改参数重跑。

**读表要点**：

1. 纯反馈即使把 `Ki` 从 1.2 加到 10（8 倍多），静差也只从 −49.7% 改善到 −19.9%
   —— 因为**摩擦死区**要求 PWM 必须超过一个阈值电机才转，
   而纯反馈在误差很小时输出不够，就卡在那里。
2. 加了前馈以后，`Ki` 只要 **0.5**（纯反馈的 1/20）就能做到 −3.4% 的稳态误差，
   而且响应快一个数量级、**零超调**。
3. 根本原因是：**前馈把"量级"直接给足了，积分项只需要补摩擦那一点点差值。**

# 二、前馈控制的原理

## 2.1 基本结构

```
                ┌──────────────┐
   目标轮速 ───►│   前馈增益    │──────┐
                └──────────────┘      │
                                      ▼
   目标轮速 ──►( + )──►┌────────┐    ( + )──► PWM ──► 电机 ──┬──► 轮速
              ▲       │  PID   │                            │
              │       └────────┘                            │
              │            ▲                                │
              └────────────┘                                │
                 误差 = 目标 − 实际  ◄───────────────────────┘
```

数学上：

```
PWM = K_ff · 目标轮速  +  PID(目标轮速 − 实际轮速)
      └──────┬──────┘     └──────────┬──────────┘
       开环已知的部分            闭环修正的部分
```

## 2.2 为什么这不算"作弊"

前馈用到的信息是**我们已经知道的**：

```
已知：PWM 给满 100 时，轮子大约转 11 rad/s
那么：想让轮子转 6 rad/s，先给 PWM ≈ 100 × 6/11 ≈ 55 是理所当然的
```

**没有理由让 PID 从 0 开始一点点猜。** 这就是前馈的全部逻辑。

## 2.3 前馈 vs 反馈的分工

| | 前馈 | 反馈（PID） |
|---|---|---|
| 依赖什么 | **模型参数**（满 PWM 对应多少转速） | **测量值**（编码器读数） |
| 能否消除静差 | ❌ 不能（模型不准就有偏差） | ✅ 能（积分项） |
| 响应速度 | **快**（不需要等误差出现） | 慢（必须等误差出现才动作） |
| 模型错了会怎样 | 响应变差，但**系统仍稳定**（PID 会补回来） | — |
| 参数怎么来 | **实测**（PWM 给满读编码器） | 整定 |

> [!important] 关键理解：前馈不改变稳定性
> 前馈是**开环**的 —— 它不构成回路，所以**不会影响闭环的稳定性**。
> 前馈填错了只会让"起点"偏一点，PID 照样把误差收掉。
> 这就是为什么可以放心地先加前馈、再整定 PID。

## 2.4 前馈增益怎么算

```c
int16_t Diff_WheelToPwm(float Wheel)
{
    float Pwm = Wheel / MOTOR_MAX_WHEEL_SPEED * 100.0f;
    /* 限幅 ±100，四舍五入 */
}
```

即：

```
K_ff = 100 / MOTOR_MAX_WHEEL_SPEED      （PWM 百分点 / (rad/s)）
```

`MOTOR_MAX_WHEEL_SPEED` **必须实测**：

| 步骤 | 操作 |
|:--:|---|
| 1 | 烧一个只做 `Motor_SetSpeed(MOTOR_L, 100)` 的简单程序 |
| 2 | 等转速稳定，读 OLED 或 VOCODE/VOFA+ 上的实际转速 |
| 3 | 那个数就是 `MOTOR_MAX_WHEEL_SPEED` |

> [!note] 本工程用的是 **11.0 rad/s**，是估算值不是实测值
> `Diff.h` 里当前填 `MOTOR_MAX_WHEEL_SPEED = 11.0f`
> （JGB37-520 1:30 / 12V 空载约 350 rpm 的估算）。
> **实测后必须改。**

## 2.5 一个容易忽略的细节：低速段的取舍

`Diff_WheelToPwm` 四舍五入到整数，所以 `|PWM| < 0.5` 会归零。
这不是 bug：

- PWM 寄存器是 0~100 的整数，0.4% 的占空比**本来也驱动不了电机**
- 这点低速死区由 PID 的积分项补 —— 前馈只负责量级

# 三、为什么必须两个独立的闭环

## 3.1 单环为什么做不了转向

假设"聪明地"用一个 PID 控制平均速度：

```
目标平均速度 = (ω_L + ω_R) / 2
```

原地转时 `ω_L = −6.15`、`ω_R = +6.15`，平均值 = **0**。

⇒ PID 的目标是 0，实际平均速度也是 0，**误差恒为 0，输出为 0**
⇒ **两个轮子都不动，转向完全无法实现。**

## 3.2 双环的结构

```
                    ┌──────────┐
   目标 ω_L ───────►│ PID 左   │──► PWM_L ──► 左电机 ──► 编码器 ──┐
                    └──────────┘                                  │
                         ▲                                        │
                         └──────────── 反馈 ω_L ◄─────────────────┘

                    ┌──────────┐
   目标 ω_R ───────►│ PID 右   │──► PWM_R ──► 右电机 ──► 编码器 ──┐
                    └──────────┘                                  │
                         ▲                                        │
                         └──────────── 反馈 ω_R ◄─────────────────┘
```

**两个环完全独立**，各有各的：

| 独立项 | 为什么必须独立 |
|---|---|
| 积分器 | 左轮的积分饱和**绝不该**影响右轮 |
| 输出限幅 | 两轮摩擦不同，需要的 PWM 本来就不同 |
| 历史误差 | 微分项基于各自的误差序列 |

## 3.3 结构体化的收益（七阶段的伏笔）

```c
PID_t SpeedPID[2];                                   /* 两个实例 */
PID_Init(&SpeedPID[MOTOR_L], PID_KP, PID_KI, PID_KD);
PID_Init(&SpeedPID[MOTOR_R], PID_KP, PID_KI, PID_KD);
```

**`PID.c` 一个字都没改。**

七阶段 `PID.h` 的注释里就写着：

```c
/* 把 PID 做成结构体，好处是**同一套代码可以开多个独立的环**：
 *   本阶段：一个速度环
 *   第八阶段：左右轮两个速度环（差速小车）
 *   以后：位置环、电流环……
 */
```

> [!important] 这就是"结构体化"的真正价值
> 新增一个环的成本是 **`PID_Init` 一次**，而不是"复制一份代码再改"。
> 复制代码的问题不是"多写几行"，而是**以后修 bug 要修两处，必然漏一处**。
>
> 与之对照：`Motor` 和 `Encoder` 也需要结构体化 ——
> 七阶段它们是"全局唯一"的写法（引脚写死在宏里），
> 第八阶段同样做成了 `Motor_t Motors[2]`。

# 四、中断服务函数的设计原则

## 4.1 三条铁律

| # | 原则 | 理由 |
|:--:|---|---|
| 1 | **短** | 中断占用 CPU 时间越长，主循环和其他中断被推迟得越久 |
| 2 | **纯** | 只做寄存器和内存操作，不做 I/O、不等待 |
| 3 | **不碰共享资源** | 与主循环共享的外设（总线、缓冲区）必须有互斥或干脆不共享 |

## 4.2 判断标准：一句话检验

> **中断里能不能只做"不需要等待"的事？**

| 操作 | 需要等待？ | 能放中断？ |
|---|---|---|
| 读寄存器（编码器计数、GPIO 电平） | 否 | ✅ |
| 浮点/整数运算 | 否 | ✅ |
| 写 PWM 比较寄存器 | 否 | ✅ |
| 置标志位 | 否 | ✅ |
| 软件 I2C（每位要延时） | **是** | ❌ |
| 串口阻塞发送 | **是** | ❌ |
| 等 DMA 完成 | **是** | ❌ |

## 4.3 小车端为什么可以放中断

小车端的 10ms 中断里做的是：

```c
void Timer_TickHook(void)
{
    Encoder_Update();                       /* 只读 TIMx->CNT 寄存器 */
    /* 两个 PID：纯浮点运算 */
    /* Motor_SetSpeed：写 GPIO 和 TIMx->CCR 寄存器 */
}
```

**全部是寄存器和内存操作，没有任何等待** —— 完全符合三条铁律。

而且 PID **必须**放中断：离散 PID 的参数里隐含了采样周期。

```
积分项等效增益 = Ki × Δt
微分项等效增益 = Kd / Δt
```

周期一抖，等效参数就跟着抖 → 出现「**调好的参数突然振荡**」这类无法复现的问题。

## 4.4 手带端为什么不能放中断（真实踩坑）

### 坑一：`Delay_us()` 把 10ms 时基干掉了

| 项 | 内容 |
|---|---|
| 起因 | 右编码器占了 TIM4，10ms 周期搬到 **SysTick**（理由：内核定时器不占外设） |
| 隐藏事实 | **江科大 `Delay.c` 的 `Delay_us()` 也用 SysTick** |
| 致命细节 | 它写 `SysTick->CTRL = 0x00000005`，其中 **TICKINT（bit1）= 0** → **把中断关掉了**；结束时写 `0x00000004`，ENABLE=0 且**不恢复我们的配置** |

```c
/* Delay.c —— 江科大原版（问题就在这两行） */
SysTick->LOAD = 72 * xus;                  /* ← 覆盖了我们 720000 的重装载值 */
SysTick->CTRL = 0x00000005;                /* ENABLE=1, CLKSOURCE=1, TICKINT=0 ← 中断没了 */
while(!(SysTick->CTRL & 0x00010000));
SysTick->CTRL = 0x00000004;                /* 结束了，但也没恢复 */
```

**后果链条**：

```
软件 I2C 每位都调 Delay_us(10)
   → SysTick 中断被永久关闭
   → 10ms 中断不再来
   → 姿态解算停止、Timer_GetMs() 冻住
   → 20ms 心跳永远发不出去
   → 小车端 500ms 超时 → 小车停下
```

**表现**：手带端 OLED 卡住不动，小车走一下就停。
一个延时函数把整个系统时基干掉了 —— 这种"看起来毫不相关"的 bug 最难查。

**最终方案**：10ms 周期改用 **TIM1**（本项目完全空闲的高级定时器），
SysTick 留给 `Delay_us` 继续用。

> [!important] 两条可复用的教训
> **① "更优雅的方案"如果和既有代码抢同一个硬件资源，就不优雅了。**
> 选方案前先把"谁还在用这个资源"查一遍：
> `grep -r "SysTick" 整个工程` 就能提前发现。
>
> **② 优先动自己的代码，别动"别人写的、到处被调用的"基础设施。**
> `Delay_us` 是江科大例程的公共设施，改它影响面未知；
> 换自己的定时器只影响本工程 —— **改动面小 = 风险小**。

**顺带一个知识点：TIM1 的中断向量名**

| 定时器 | 更新中断向量 |
|---|---|
| TIM2~TIM4 | `TIMx_IRQHandler` |
| **TIM1（高级）** | **`TIM1_UP_IRQHandler`** |

TIM1 有 4 个独立向量：`TIM1_BRK` / `TIM1_UP` / `TIM1_TRG_COM` / `TIM1_CC`。
**写成 `TIM1_IRQHandler` 的表现是：能编译、定时器在跑，但永远不进中断。**

### 坑二：中断里做 I2C 导致 OLED 花屏

| 项 | 内容 |
|---|---|
| 起因 | `Attitude_Update()` 既读 MPU6050 又做滤波，放在 10ms 中断里 |
| 问题一（耗时） | 软件 I2C 每位 `Delay_us(10)`，读 14 字节约 **5ms**，加温度 2.4ms → 接近 **7ms**，10ms 周期里占 70% |
| 问题二（**更致命**） | MPU6050 与 OLED **共用 PB8/PB9**。中断随时打断主循环，两段 I2C 时序**互相插入** |
| 表现 | OLED 花屏 + 姿态读数错乱，**极难复现** |

**时序错乱示意**：

```
主循环：给 OLED 发字节 0x78  [SCL↑][SCL↓][SCL↑]...
                              ↓ 中断来了（约 5ms）
中断  ：开始读 MPU6050        [SCL↑][SDA 采样]...
主循环：...接着发 [SCL↓][SCL↑]
         ↑ 这两段时钟混在一起，OLED 收到的字节已经错了
```

**解决方案**：把「采样」和「滤波」拆开

```c
/* Attitude.h —— 拆成两个接口 */
void Attitude_Sample(void);         /* 主循环：读 MPU6050（含 I2C） */
void Attitude_FilterUpdate(void);   /* 中断：只做纯数学 */

/* 中断 */
void Timer_TickHook(void)
{
    SampleFlag = 1;                 /* 通知主循环：该采样了 */
    Attitude_FilterUpdate();        /* 用上次的采样值做滤波 */
}

/* 主循环 */
if (SampleFlag) { SampleFlag = 0; Attitude_Sample(); }
```

**为什么这样就安全了**：
I2C 全部发生在**主循环**里，和 OLED 天然**串行** —— 不需要任何锁、任何原子操作。

> [!important] 这是"资源共享"的经典解法
> 面对共享资源，只有两种正确做法：
> ① **加互斥**（关中断、信号量、总线忙标志）—— 复杂、容易死锁
> ② **消除并发**（让两者跑在同一个上下文里）—— 简单、无锁
>
> 本工程选了 ②：**把 I2C 都放在主循环**。
> 经验：**能靠"消除并发"解决的就不要靠"加锁"解决。**

### 代价与补偿

拆分后滤波的调用时刻有几毫秒抖动。为什么可接受：

| 理由 | 说明 |
|---|---|
| 滤波对间隔抖动不敏感 | 互补滤波系数 0.98，几毫秒的 dt 误差影响在千分之几度 |
| 用的是**实际**采样间隔 | 代码里用 `SamplesInWindow` 统计，不是写死 10ms |
| 与 PID 的要求不同 | PID 的参数**隐含**采样周期（必须严格固定）；姿态滤波没有这个约束 |

> [!tip] 不要混为一谈
> 「PID 必须严格固定周期」≠「所有周期性任务都必须严格固定周期」。
> 判断依据是：**这个算法的参数里有没有隐含 dt？**
> PID 有（Ki×Δt、Kd/Δt），互补滤波没有。

# 五、多层安全设计

## 5.1 为什么要"多层"

一次失效就导致事故的系统是不可接受的。每加一层，就多一道防线：

```
第 1 层  上电默认停机          → 防上电乱窜
第 2 层  协议层限幅            → 防错帧/噪声把目标设成荒谬值
第 3 层  电机能力包络          → 防物理上做不到的指令
第 4 层  PID 输出/积分限幅      → 防积分饱和冲出去
第 5 层  500ms 失联保护         → 防掉线后小车继续跑
第 6 层  速度档位按键（含0%急停）→ 人肉兜底
```

## 5.2 失联保护为什么必须"三件事一起做"

```c
if (Timer_GetMs() - LastRxMs > LINK_TIMEOUT_MS)
{
    if (LinkLost == 0)
    {
        LinkLost = 1;
        /* ① 清目标 */  TargetWheel[..] = 0;  PID_SetTarget(.., 0);
        /* ② 清积分 */  PID_Reset(..);
        /* ③ 停机   */  Motor_StopAll();
    }
}
```

| 只做其中一部分 | 后果 |
|---|---|
| 只停机不清目标 | 链路恢复瞬间 PID 目标还是旧的 → **猛冲一下** |
| 只清目标不清积分 | 历史积分仍在 → 输出不为 0 → 恢复时**窜一下** |
| 清目标清积分但不停机 | 上一条指令的 PWM 还在 → 小车继续跑 |

## 5.3 自由停止 vs 刹车（题目要的是"不发力"）

| | 自由停止（AIN=00） | 刹车（AIN=11） |
|---|---|---|
| 电机两端 | 悬空 | 短路 |
| 反电动势 | 无回路 | 形成制动电流 |
| 效果 | 惯性滑行慢慢停 | 快速制动 |
| 是否"发力" | **否** ← 题目要求这个 | 有制动力 |

## 5.4 速度档位按键的一个细节

档位衰减必须**从原始值算**，不能在上次结果上累乘：

```c
/* ✗ 错误：每按一次就在上次结果上再乘一次 */
TargetV = TargetV * Scale;                  /* 按 3 次 50% → 只剩 12.5% */

/* ✓ 正确：原始值只存一份，每次重新算 */
TargetV = RawV * Scale;
```

**并且失联时要跳过重算**：否则会把目标重新设成非零值，
而输出被 `Motor_Stop` 挡着 → 积分器一路充到限幅 → 链路恢复瞬间"窜"一下。

# 六、调试方法论：「一次只引入一个新变量」

## 6.1 为什么顺序不能跳

如果一上电就"全部接好、全部打开"，出问题时：

```
小车不走
  ├─ 是电机接线错？        ├─ 是编码器方向反？
  ├─ 是蓝牙没通？          ├─ 是手势映射错？
  ├─ 是 PID 参数不对？     └─ 是引脚接错？
```

**七八个可能同时存在，无法定位。**

按"一次只引入一个新变量"的顺序，每一步只增加**一个**不确定性：

```
架起小车  →  不接蓝牙  →  同号性  →  转向方向  →  接蓝牙  →  手势  →  整定 PID
   ↑            ↑           ↑          ↑           ↑          ↑         ↑
 机械       显示/按键    反馈方向   执行方向     链路       映射      参数
```

**任一步失败，原因只可能在那一步引入的新东西里。**

## 6.2 这套方法论在项目里的三次体现

| 阶段 | 做法 | 只引入了什么新变量 |
|---|---|---|
| 三阶段 | 有线双机 → 四阶段换蓝牙 | 通信**介质** |
| 六阶段 | 离散手势 → 七阶段连续映射 | 映射**方式** |
| 八阶段 | 七阶段单电机 → 八阶段双电机 | **执行器数量** |

> [!important] 这条原则的另一种说法
> 也叫「**分层验证**」：先证明底层是对的，再在上面加一层。
> 好处不只是"好调试"，更重要的是 ——
> **底层对了以后，上层出问题就只需要看上层。**

## 6.3 本阶段"底层"是哪一层

第八阶段的底层是**编码器方向（同号性）**。理由：

```
如果编码器与电机反号 → 速度环变成正反馈 → 一上电就飞车
```

这**不是"效果差一点"，而是"会撞坏东西"**。所以它必须最先验证。

**验证方法**：给一个固定的小正 PWM（开环，PID 不参与），
看两轮的实际读数**是否都为正**。哪个为负就改对应的 `ENCODER_DIR_x`。

# 九、七条可复用的原则

| # | 原则 | 本任务中的体现 |
|:--:|---|---|
| 1 | **已知的信息就不要再让反馈去猜** | 前馈把量级直接给足 |
| 2 | **开环补偿不影响闭环稳定性** | 所以前馈可以先加、再加 PID |
| 3 | **一个环管不了两个自由度** | 平均速度环无法实现转向 |
| 4 | **中断必须短、纯、不碰共享资源** | 手带端把 I2C 移出中断 |
| 5 | **能"消除并发"就不要"加锁"** | I2C 全部放主循环，无需互斥 |
| 6 | **优先动自己的代码，别动公共基础设施** | 换定时器而不是改 `Delay_us` |
| 7 | **一次只引入一个新变量** | 11 步调试顺序 |
